# Chinese Chess: casual completion and local analysis

Date: 2026-10-02

- Rename the product to Chinese Chess. Keep repository/deployment identifiers and legacy browser storage/cookie keys so existing links, sessions, and local games survive the rename.
- Existing accounts have no email. Add opt-in random 256-bit single-use recovery codes instead of inventing email ownership or silently moving accounts to a new identity provider. Only SHA-256 hashes are stored. Issuing a code requires the current password; redemption consumes it, changes the password and revokes all sessions transactionally. Users must save a code before losing access. Managed verified-email auth and production email remain separate launch work.
- Account deletion requires password confirmation and no active seat. Remove private practice, recovery credentials, sessions and command receipts containing the old name. Retain shared game records under a random anonymous username. Serialize deletion with seating to prevent a deleted account rejoining through an in-flight request.
- A rematch is a mutually accepted command on a completed game. Lock the matchmaking guard before the game, enforce participant/version/receipt checks, reserve both seats atomically, swap colors, and create exactly one casual game. Reviewing an old game never automatically redirects; only a newly accepted rematch while the players are present does.
- Post-game analysis is an on-demand browser Worker with no API calls, writes, or persistent cache. Analyze legal replay moves at the same completed search depth; discard incomplete deeper iterations. UI labels all evaluations as lightweight estimates. Terminate workers on close/navigation. Do not mount analysis for a live online game.
- Settle casual timeouts using an invoker-only function in a non-exposed private schema, scheduled through Supabase pg_cron every minute. It locks overdue rows with SKIP LOCKED and uses persisted deadlines, version increments and atomic seat release. Rated rows are excluded because their finalization must include rating events. Keep the existing server sweep for that future path and for explicit maintenance.
- Rated play stays hard-disabled. Existing movement differential tests and rating transaction tests do not establish WXF chase/no-progress conformance. No claim of full competition certification or actual iPhone verification is made.
